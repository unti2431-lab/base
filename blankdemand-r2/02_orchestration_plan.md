## 1. 구조

```
                ┌──────────────────────────────────────────────┐
                │ L0 오케스트레이터 (ChatGPT Work)               │
                │  STATUS.md · 계약 버전 · 작업카드 발행 · 관문 심사  │
                └──────┬──────────────▲─────────────────────────┘
          작업카드(TASK) │              │ HANDOFF / RUNLOG (프로젝트 소스로 저장)
   ┌─────────┬─────────┼─────────┬────┴────┬─────────┐
   ▼         ▼         ▼         ▼         ▼         ▼
  L1        L2        L3        L4        L5        L6
 요건·     데이터    기준·     검증기·   화면·     레시피
 선행연구  파이프    평가      반증      시연      문서
                        │         ▲
                        └─ 출력 ──┘  (L4가 L3 결과를 매 라운드 반증 리뷰)

  사람(통합자): 레인 산출 코드 → 로컬 git 폴더 → 실행 → RUNLOG를 프로젝트에 업로드
```

### 레인 정의

| 레인 | 이름 | 소유 경로(이 레인만 수정) | 주 산출물 | 시작 조건 |
|---|---|---|---|---|
| **L0** | 오케스트레이터 | `STATUS.md`, `contracts/` | 작업카드, 관문 판정, 계약 버전 | 즉시 |
| **L1** | 요건·선행연구 | `docs/research/` | 요건표, 문의문, 선행연구 대조표, 기존 레시피 중복 대조, 인터뷰 섭외문 | 즉시 |
| **L2** | 데이터 | `src/data/`, `data/manifest/` | 다운로드·해시, 층화 표본(20→200), 스키마 검사, `split.json`, 특성 시점표 | 즉시 |
| **L3** | 기준·평가 | `src/model/`, `src/eval/` | B0·B2·W, 비용함수, 마스킹 평가, 판정 규칙 v0 구현, 지표표 | 계약 v0 (합성 입력으로 선행 가능) |
| **L4** | 검증기·반증 | `src/validate/`, `tests/` | 실패시험 12종, 레드라인 검사기(정상 0·관측 하한·누수·제약), 라운드별 반증 리뷰 | 즉시(합성 입력) |
| **L5** | 화면·시연 | `app/`, `demo/` | Streamlit 1화면(CSV 입력→근거표→내보내기), 시연 대본·녹화 체크리스트 | 계약 v0 (목업 JSON으로 선행) |
| **L6** | 레시피 문서 | `docs/recipe/` | 레시피 본문(공식 양식), AI 사용 내역, 한계 절, 출처, 결정 기록 | 즉시(골격) |

**병렬화의 핵심은 계약(contract)을 먼저 고정하는 것**이다. L0이 0시간 차에 `contracts/v0`(입력 스키마·판정 출력 JSON·특성 시점표)를 발행하면, L3·L4·L5는 실데이터가 오기 전부터 합성/목업 입력으로 동시에 진행할 수 있다. 실데이터가 도착하면 입력만 바꾼다.

## 2. 통신 규약

### 2.1 파일 이름 (프로젝트 소스)

| 종류 | 이름 형식 | 작성자 |
|---|---|---|
| 상태판 | `STATUS.md` (항상 최신 1개, 덮어씀) | L0 |
| 계약 | `contracts_vN.md` | L0만 |
| 작업카드 | `TASK_L3_1009_R1.md` | L0 |
| 인계 | `HO_L3_1009_R1.md` | 각 레인 |
| 실행 기록 | `RUNLOG_1009_R1.txt` | 사람(로컬 실행 결과 그대로) |
| 결정 기록 | `DECISION_G1.md` | L0 초안 → 사람 확정 |

- 레인이 응답 끝에 HANDOFF 블록을 내면, 사람은 **그 응답을 프로젝트 소스로 저장**(또는 .md 파일로 업로드)한다.
- 코드는 채팅에서 복사하지 말고 **파일 다운로드 → 로컬 git 폴더**에 넣고 커밋한다. 커밋 메시지에 `[L3 R1]`처럼 레인·라운드를 붙인다.

### 2.2 HANDOFF 블록 (모든 레인 공통, 응답 맨 끝)

```
=== HANDOFF L? / R? / YYYY-MM-DD HH:MM ===
산출물: 파일명 — 한 줄 설명 (소유 경로 안에서만)
실행 방법: 로컬에서 돌릴 명령 (없으면 "없음")
기대 결과: RUNLOG에서 확인할 것 (숫자 예상치는 쓰지 않음, 형식만)
계약 의존: contracts_vN (변경 요청이 있으면 "변경요청: ...")
미해결: 남은 문제 / 막힌 이유
다음 요청: L0 또는 다른 레인에 필요한 것
숫자 출처: 이 응답의 모든 숫자 → [RUNLOG 파일명] / [자료 출처] / [제안값]
AI 사용: 이 응답에서 AI가 만든 것(코드/문장/조사) 한 줄
=== END ===
```

### 2.3 공통 금지 규칙 (프로젝트 지침에 넣음)

1. **RUNLOG에 없는 성능 숫자를 만들지 않는다.** 예상치·예시 숫자도 쓰지 않는다.
2. 자기 소유 경로 밖의 파일을 수정하지 않는다. 필요하면 "다음 요청"에 적는다.
3. 계약을 바꾸지 않는다. 변경은 L0에 요청 → L0이 `contracts_vN+1` 발행.
4. 실제 개수·원화·국내 효과로 환산하지 않는다(정규화 데이터).
5. 시연·문서에서 녹화 재생을 실시간 분석으로 부르지 않는다.
6. 모르는 것은 [미확인]으로 남긴다. 추측으로 공고 조건을 채우지 않는다.

## 3. 진행 방식 — 라운드와 관문

### 3.1 라운드(1회 60~120분)

```
① L0: STATUS 갱신 + 레인별 TASK 카드 발행        (사람: 카드를 각 채팅에 붙여넣기, 5분)
② L1~L6 동시 작업 → HANDOFF                      (사람: 대기 또는 다른 일)
③ 사람: 코드 수령 → 로컬 실행 → RUNLOG 업로드      (20~40분)
④ L4: RUNLOG·L3 출력에 대한 반증 리뷰 HANDOFF      (10분)
⑤ L0: HANDOFF·RUNLOG 종합 → 다음 라운드 카드 / 관문 판정 초안
```

하루 2~3라운드. 사람이 실제로 쓰는 시간은 ①③⑤의 확인이며, 레인이 일하는 동안 사람은 문의 전화·인터뷰 섭외·녹화 같은 **사람만 할 수 있는 일**을 한다.

### 3.2 관문(Gate)

| 관문 | 시점 | 통과 조건 (전부 RUNLOG/파일로 증명) | 실패 시 |
|---|---|---|---|
| **G0** | 10/8 밤 | 프로젝트·계약 v0·레인 6개 가동, 문의 발신, 다운로드 시작 | 다음 날 오전 반복 |
| **G1** | 10/9 밤 | 실데이터 표본(최소 20, 목표 200) + 해시 + 스키마 검사 통과 + `split.json` + B0 결과 | **R2 중단 기준 적용**: 학습·시연 확장 중지, 검사기만 합성으로 계속. 과제 교체 금지 |

## 5. 오늘 10분 셋업 순서

1. ChatGPT에서 프로젝트 **"빈칸수요 R2.1"** 생성.
2. 프로젝트 지침(Instructions)에 `04_lane_prompts.md`의 **[공통 프로젝트 지침]** 붙여넣기.
3. 프로젝트 소스로 업로드: 원본 R2 docx, `01_review_R2.1.md`, `02_orchestration_plan.md`, `03_contracts_v0.md`, `04_lane_prompts.md`.
4. 프로젝트 안에서 **ChatGPT Work** 대화를 열고 L0 프롬프트 붙여넣기 → STATUS·계약 확인 응답 받기.
5. 같은 프로젝트에 새 채팅 6개(L1~L6)를 열고, 채팅 이름을 `L1 요건` … `L6 문서`로 바꾼 뒤 각 레인 프롬프트(첫 작업카드 포함) 붙여넣기.
6. 로컬에 작업 폴더 생성(아래 구조), `git init`.

```
blankdemand/
  STATUS.md  contracts/  data/{raw,sample,manifest}/  src/{data,model,eval,validate}/
  tests/  app/  demo/  docs/{research,recipe}/  runlogs/  v1_reuse/ (원본 v1 — 읽기 전용)
```

## 7. 위험과 대응

| 위험 | 신호 | 대응 |
|---|---|---|
| 레인 간 계약 불일치 | 코드가 서로 다른 필드명을 씀 | L0만 계약 수정, 모든 HANDOFF에 계약 버전 기재 |
| 숫자 환각 | HANDOFF "숫자 출처" 칸 누락 | L0이 반려, 문서 반영 금지 |
| 같은 파일 동시 수정 | git 충돌 | 소유 경로 규칙, 충돌 시 L0이 소유 레인 판정 |
| 사람이 병목 | RUNLOG 업로드 지연으로 라운드 정지 | 라운드당 실행 명령을 한 줄 `make round` 스크립트로 묶음(L2가 작성) |
| 데이터 다운로드 실패 | G1 전 표본 없음 | 공식 저장소만 사용(미러 금지), 합성 입력으로 검사기만 진행, R2 중단 기준 |
| Work/채팅 한도 소진 | 응답 지연·제한 | 우선순위 L2>L3>L4>L5>L6>L1 순으로 라운드 축소 |
| 모델 변경(10/14 등) | 응답 스타일·형식 변화 | 프롬프트·계약은 파일로 유지, 첫 응답에서 HANDOFF 형식 재확인 |
| 선행연구가 거의 같은 기여를 이미 함 | L1 대조표에서 확인 | 기여를 "발주안 검증·보류·근거표"로 좁히고, 겹치는 부분은 인용·재사용으로 명시 |
